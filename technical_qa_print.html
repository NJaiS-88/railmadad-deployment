🚆 RailMadad — Technical Deep Dive Q&A

1. 🔍 Has OCR been implemented? (Tesseract?)

What OCR is

OCR = Optical Character Recognition. It reads text from images — like the coach number printed on the side of a railway coach.

What's implemented

YES, OCR is implemented — but NOT using Tesseract. There are two OCR use-cases:

A) Coach Number OCR (Verification Agent)

File: backend/agents/verification_agent/tools/ocr_tool.py

It reads the coach number from the evidence photo and compares it to what the passenger claimed. It uses:

  1. Filename pattern matching (regex) for test images
  2. Sidecar .txt file (where a real OCR engine would write its output)
  3. Fallback mock rules (e.g., B7 is detected as B4 to simulate a mismatch)

Then it runs Levenshtein edit distance (implemented from scratch, no library) to handle OCR character confusions like 8→B, 5→S, 1→I. If edit distance > 1, it's flagged as a mismatch.

# Actual code from ocr_tool.py
normalization_map = {'8': 'B', '5': 'S', '1': 'I'}
edit_dist = LevenshteinDistance(norm_entered, norm_detected)
coach_match = (edit_dist == 0)

B) Staff ID Card OCR

File: ml_service.py → /scan-id-card endpoint

Uses OpenRouter AI vision cascade (thinkingmachines/inkling, meta-llama/llama-3.2-11b-vision-instruct, google/gemini-2.0-flash-001) — it reads the Railway ID card photo, extracts the employee's name, and compares it to the typed name. Returns detected_name, match, confidence, and reason. Fallback: if AI is offline, it approves with 70% confidence.

Why not Tesseract?

Tesseract requires system binary installation and struggles with printed railway coach fonts and skewed/outdoor photos. The OpenRouter multimodal vision models are far more robust for real-world images. The coach OCR tool is architected with a sidecar .txt file slot specifically so a real Tesseract integration can be plugged in later without changing any other code.

2. 📊 Confidence Score — How is it decided?

What it is

A score from 0–100 representing how certain the AI is that it fully understands the complaint and can route it correctly without a human officer.

How the AI decides it (the exact prompt)

The LLM (OpenRouter meta-llama/llama-3.3-70b-instruct) is given these exact calibration instructions in ml_service.py:

"CRITICAL INSTRUCTIONS FOR 'confidence':
- Include an explicit integer 'confidence' from 0 to 100.
- It reflects how SURE you are that you fully understand the issue context
  and could route it to the right department automatically WITHOUT an officer.
- 85-100: fully or mostly sure — clear issue, clear context, no ambiguity.
- 60-84: some self-doubt — meaningful but details could be misinterpreted.
- 30-59: significant doubt — vague, contradictory, or confusing content.
- 0-29: totally unclear or unrelated content.
- Be honest and calibrated; lower the score whenever you feel you might be guessing."

Score calculation (post-LLM)

If the LLM returns confidence: 0 or an invalid value, the backend derives a fallback deterministically:

ConditionConfidence
relevance = "unrelated"10
relevance = "partially_related"55
is_sufficient=true AND has_issue=true85
Anything else40

How it gates routing (the threshold)

# In ml_service.py — line 770
if suff and confidence >= 85 and not llm_doubt and journey_certain:
    # AUTO-VERIFY — no officer needed
else:
    # MANUAL OFFICER REVIEW

So 85 is the auto-verify threshold. Everything below goes to the officer queue.

3. 🎲 DICE — What is it? Is it implemented?

What DICE is (conceptually)

DICE = Duplicate/Incident Correlation Engine. The idea: if 7 passengers all report "AC not working" in coach B4 on Train 12001, these shouldn't be 7 separate officer tasks — they should be one merged incident ticket.

The term "DICE" was used in your presentation but is not the formal name used in the codebase.

What IS implemented

The Clusters feature in the Officer Dashboard is the direct implementation of DICE.

File: backend/routes/officerRoutes.js → GET /officer/clusters

// Groups complaints by: category + trainNumber
const buildClusterKey = (complaint) => {
  const category = deriveComplaintCategory(complaint);
  const train = complaint?.trainNumber || 'N/A';
  return `${category}|${train}`;
};

Every active complaint is grouped into a bucket by this key. Each bucket = one cluster/incident. The API returns the top 8 clusters sorted by how many complaints they contain.

Officer action: "Confirm as One Incident" → POST /officer/clusters/:id/confirm.

What's NOT implemented

  • True complaint merging (child complaints are not actually linked to a parent in the DB yet — the confirm endpoint stubs { ok: true, confirmed: true })
  • NLP-based semantic similarity (currently groups only on exact category+train key, not on description meaning)

Future improvement

Replace the buildClusterKey string match with a sentence embedding similarity (e.g., sentence-transformers/all-MiniLM-L6-v2) and cluster on cosine similarity > 0.85.

4. 🎬 FFmpeg — What is it? Is it implemented?

What FFmpeg is

FFmpeg is a free, open-source command-line tool for processing video and audio. It can convert, trim, extract audio from video, change codecs, etc. It is the industry-standard for media processing.

Why it's needed here

Browsers record video as WebM (a format OpenCV on Windows cannot decode). Whisper also needs a clean WAV file for transcription. FFmpeg bridges this gap.

Exactly how it's implemented

File: ml_service.py

# Step 1: Passenger records video → browser sends base64 WebM to ML service
# Step 2: Save to temp file
with tempfile.NamedTemporaryFile(delete=False, suffix=".webm") as tmp:
    tmp.write(video_bytes)
    raw_path = tmp.name

# Step 3: FFmpeg transcodes WebM → H264 MP4 (for OpenCV frame sampling)
subprocess.run([FFMPEG_EXE, "-y", "-i", raw_path,
    "-c:v", "libx264", "-preset", "ultrafast", "-crf", "28",
    "-c:a", "aac", mp4_path], timeout=90)

# Step 4: FFmpeg extracts audio → 16kHz mono WAV (for Whisper)
subprocess.run([FFMPEG_EXE, "-y", "-i", raw_path,
    "-vn", "-acodec", "pcm_s16le", "-ar", "16000", "-ac", "1", wav_path], timeout=60)

# Step 5: Whisper transcribes the WAV
# Step 6: BLIP captions sampled frames from the MP4
# Step 7: Both results merged into multimodal paragraph → sent to LLM

FFmpeg is also used for audio-only complaints (voice notes), converting browser WebM audio → WAV before Whisper transcription.

The system prefers system-installed FFmpeg (auto-detected via shutil.which("ffmpeg")), with imageio_ffmpeg as a Python fallback.

6. 📐 Haversine Distance — What is it? Is it implemented?

What it is

Haversine is a mathematical formula that calculates the shortest distance between two GPS coordinates on Earth's curved surface (great-circle distance).

Formula:

a = sin²(Δlat/2) + cos(lat1)·cos(lat2)·sin²(Δlon/2)
distance = 2 × R × arcsin(√a)     [R = 6371 km]

Implemented in TWO places:

Place 1: Staff Assignment (staffAssignmentService.js)

function haversineKm(a, b) {
  const dLat = toRadians(lat2 - lat1);
  const dLon = toRadians(lon2 - lon1);
  const x = Math.sin(dLat/2)**2 + Math.cos(lat1Rad)*Math.cos(lat2Rad)*Math.sin(dLon/2)**2;
  return 2 * 6371 * Math.asin(Math.sqrt(x));
}

Used to rank available staff by distance to the complaint GPS location. Nearest staff with the right department gets assigned first.

Place 2: Verification Agent (tools/distance_tool.py)

Measures distance between photo EXIF GPS and live train GPS. Flagged if > 5 km apart.

7. 📍 GPS — How is it captured?

Three separate GPS sources in this project:

  1. Passenger's device GPS (Browser navigator.geolocation): In ReportFlow.jsx, captures client lat/lng.
  2. Photo EXIF GPS metadata: In exif_tool.py, Pillow extracts embedded GPS latitude/longitude from camera metadata.
  3. Live Train Position (RailRadar API): In train_position_tool.py, calls api.railradar.in/v1/trains/{trainNumber}/live for live telemetry.

Verification: If distance between Photo GPS and Train GPS > 5 km, suspicion score increases.

Honest answer: Not explicitly implemented

  • Future Roadmap: Geohash fuzzing (~1.1km radius), EXIF GPS stripping post-verification, role-based location redaction, ephemeral location retention.

10. ⚡ What if Millions of Complaints Arrive?

  • Message Queue: Decouple submission from AI via Redis + BullMQ / Kafka.
  • Horizontal Pod Autoscaling: Scale Python ML workers on Kubernetes.
  • Database Sharding: Shard MongoDB by trainNumber or Zone.
  • Object Storage: Direct S3 presigned upload for images/videos instead of base64 in DB.
  • Caching: Redis cache with TTL for officer analytics queries.

12. 🔮 Predictive Maintenance — Is it implemented?

YES — in backend/routes/officerRoutes.js → GET /officer/hotspots

Groups complaints by trainNumber + coach. If complaints ≥ 2, computes risk score and assigns Maintenance Priority (High if ≥5, Medium if ≥3, Low otherwise). Highlights recurring coach defects before catastrophic failures occur.

14. ⭐ What if Feedback is Bad? Is it implemented?

  • Passenger rating (1–5 stars) is stored in MongoDB per complaint.
  • Staff performance & average ratings are calculated live and displayed on dashboards.
  • Future: Automatic supervisor alerts on 1–2 star ratings, automatic ticket re-opening, and rating-weighted staff task routing.

15. 🏗️ Why Not Put Everything in One Backend?

  • Language barrier: PyTorch, Whisper, and BLIP require Python; Node.js handles async I/O.
  • Resource isolation: Heavy ML models (~500MB+ RAM) will not crash or block the main REST API.
  • Independent scaling: ML workers can be scaled horizontally without multiplying API servers.
  • Fault isolation: An ML service crash will not take down authentication or complaint ingestion.
